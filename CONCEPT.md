# AIOWA: концепт (редакция от 2026-10-16)

Живой документ. Кода ещё нет; это сведённая позиция по итогам исследования фактов, восьми экспертных разборов и критики полноты. Статусы решений: **принято** (менять только через явную запись в этом файле) и **обсуждается** (ждёт решения автора или результатов спайка). Там, где эксперты разошлись, приведены обе позиции и рекомендация архитектора.

## 0. Поправки автора после синтеза (16.10.2026, вечер)

Эти решения автор принял, пока шла проработка; они имеют приоритет над текстом ниже. Таблица в разделе 2 и затронутые места в разделах 1, 5, 7, 9, 11 и 12 уже исправлены.

- **Внешние модели разрешены.** Содержимое рабочей почты можно отправлять в облачные API (ключи есть или будут) и на собственные серверы автора с моделями на мощных машинах (OpenAI-совместимый endpoint: vLLM, Ollama, LM Studio server). Рекомендация экспертов «только локальные по умолчанию» снята; меры из раздела 7 (предпросмотр контекста, локальный журнал обращений, авто-блок по меткам) сохраняются.
- **Вход — forms-based auth без MFA.** Программный вход из Rust через форму OWA, пароль в Credential Manager, тихий повторный вход при истечении сессии. Webview-логин остаётся запасным путём на случай ADFS/MFA.
- **Календарь в v1.** Автор пользуется им ежедневно; объём и этап — раздел 9.
- **Машина известна** — раздел 12. GPU для моделей на ноутбуке нет, поэтому тяжёлые модели и, при желании, эмбеддинги выносятся на серверы автора по сети.
- **Облака Microsoft 365 не будет.** Принципиальная позиция ИТ компании: всё на своих серверах (ответ автора 16.10.2026). Путь платформы: Exchange 2019 → Exchange SE on-prem. Транспорт Graph из плана исключён; OWA JSON с EWS SOAP как страховкой становятся долгосрочной ставкой, а не временной. Риск «смена платформы» в разделе 10 понижен.
- **Репозиторий заведён:** https://github.com/zergont/AIOWA (16.10.2026, пустой на момент записи). Локальная папка ещё не инициализирована; первый коммит — этот документ, опросник и проработки из `docs`, с `.gitignore` на базы, журналы, cookies и локальные сборки.
- **Почта на 99,5 % русская** (ответ автора 16.10.2026). Следствия: модели эмбеддингов выбираем из лидеров ruMTEB (FRIDA, Giga-Embeddings, USER-bge-m3), а не универсальные; русский стемминг в FTS обязателен; резолв имён с отчествами, уменьшительными и падежами важнее транслита; локальная LLM для «Совета» оценивается в первую очередь по русскому (T-lite / T-pro, Qwen3, GigaChat); золотой набор запросов почти целиком русский; английский обрабатывается, но не оптимизируется.
- **Политика по моделям** (ответ автора 16.10.2026): MVP только у автора и с его ящиком, разрешены API любых моделей, облачных и локальных. После обкатки на ящиках сотрудников без чувствительных данных принимается решение о развитии и о режиме: только локальные модели, доверенные облачные, или облако после обезличивания локальной моделью. Архитектура шлюза моделей с четырьмя режимами — новый раздел 5.6.
- **Открыто:** доступ к OWA без VPN и прокси в офисе (ушло в опросник админам); важность поиска по вложениям.

## 1. Что это и для кого

AIOWA — оффлайн почтовый клиент для корпоративного on-prem Exchange Server (сейчас 2019 CU15, build 15.2.1748.39 в пути `/owa/prem/`), повторяющий лёгкость и клавиатурную модель браузерной OWA и добавляющий локальный ИИ-слой: поиск по почте естественным языком и кнопку «Совет» при ответе на письмо. Главная практическая ценность — мгновенный локальный поиск по ящику около 100 ГБ, недоступный в серверной OWA, и ответы, написанные в стиле автора с учётом всего треда. Аудитория v1 — сам автор: один разработчик с ИИ-ассистентом, одна учётная запись, один ПК под Windows 11. Распространение коллегам и тем более публичный релиз — отдельное решение (раздел 11, п. 12), от которого зависят подпись бинарника, лицензии моделей, досье для ИБ и даже имя проекта. Это не замена Outlook для организации: правила, делегаты и прочее в v1 закрываются встроенной настоящей OWA или ссылкой «открыть в OWA»; календарь, по решению автора, входит в v1 (раздел 9).

## 3. Что проверили

Честно и в начале: **три допущения исходного концепта в сформулированном виде не подтвердились.**

1. «JSON API OWA зеркалит EWS, endpoint `/owa/service.svc` и маппинг на .NET-типы EWS подтверждены». Цитируемые источники (KB 3176540, справка EWS) этого не доказывают: KB подтверждает только тип `FindConversationJsonRequest` и соглашение имён `*JsonRequest`, причём для Exchange 2013/2016. Сам API существует, но его форма (конверт, обязательные заголовки, набор действий) должна быть снята с живого трафика. Это не ломает ставку, но делает спайк обязательным.
2. «Вход через webview работает при любом методе, включая MFA/ADFS». Подтверждено только для forms-based auth on-prem. Для ADFS/claims, Conditional Access и Microsoft 365 воспроизведённая из приложения cookie-сессия может отклоняться; Microsoft не рекомендует встроенные webview для входа. Какой метод стоит на нашем сервере — неизвестно.
3. «Exchange SE = тот же протокол». SE RTM кодово равен 2019 CU15 на момент выхода (1 июля 2025), но с тех пор SE RTM получил хотфиксы и SU, менявшие слой OWA (август 2026 отключил OWA Light). Утверждение верно только при одинаковом уровне SU, и протокол надо перепроверять после каждого SU, а не только после CU1.

Также устарели или неточны несколько технических тезисов экспертов: «bge-m3 в пределах шума с русскими моделями на retrieval» (опровергнуто: FRIDA даёт +2,4 nDCG@10), «в Rust нет крейта для вырезания подписей» (есть langmail, но без кириллицы), версии зависимостей в архитектурном разборе (ниже — проверенные).

## 4. Архитектура

### 4.1. Компоненты и потоки данных

```
[WebView2: окно входа OWA] --cookies--> [SessionManager] --Session--> [MailTransport (OWA JSON | EWS | Fake)]
                                                                            |
[TaskSupervisor: sync / backfill / index / outbox]  <---- дельты, тела ------+
        |                     |
   [Store writer actor] --> mail.db (folders, items, bodies zstd, participants, attachments_meta, sync_state, outbox)
        |                     |
   [Indexer process] ------> index.db (FTS5 external-content, chunks, vec_chunks, index_state)
        |
   [Search engine: парсер запроса -> FTS5 + vec KNN -> RRF -> группировка по тредам -> (реранкер)]
        |
   [Tauri IPC: команды + Channel] --> [Svelte 5 UI] ; письма -> ammonia -> sandbox-iframe (aiowa-mail://)
        |
   [ChatProvider (Ollama | OpenAI-compat | Anthropic) + Policy local-only] <- «Совет», разбор запроса
```

Принципы: состояние почты (прочитано, флаги, папки, черновики) живёт на сервере и зеркалится через те же операции, что делает OWA; локально уникальны только ИИ-артефакты (эмбеддинги, стилевые профили, кэш разборов). `index.db` всегда перестраиваем из `mail.db`, `mail.db` — из сервера. Любой список в UI — keyset-пагинация из SQLite страницами по 100–200 строк, никаких массивов на сотни тысяч элементов через IPC.

### 4.2. Границы trait

**`MailTransport`** (уровень операций EWS-схемы, не HTTP): `sync_folder_hierarchy`, `sync_folder_items(folder, state, max≤512, shape)`, `get_items(ids, shape)`, `get_conversation_items`, `get_attachment`, `create_item(disposition)`, `update_item(id+change_key)`, `move_items`, `delete_items(MoveToDeletedItems)`, `resolve_names`, `capabilities()`. Реализации: `OwaJson` (v1), `FakeExchange` (v1, тесты), `EwsSoap` (по необходимости), `Graph` (при M365). DTO толерантны к схеме (`#[serde(default)]`, без `deny_unknown_fields`, захват неизвестных полей в `extra` с логом на уровне debug — ранний детектор дрейфа).

**`TransportError`** с предикатами `is_retryable()` и `needs_reauth()`: `SessionExpired`, `Throttled{retry_after}`, `Network`, `Protocol{action, raw}` (не ретраить, сохранить сырой ответ), `Server{code}`, `Cancelled`.

**`SessionManager`**: single-flight повторный вход с generation-счётчиком; при `SessionExpired` все задачи переходят в `AuthRequired`, открывается одно окно входа, никаких фоновых повторов с теми же учётными данными (защита от блокировки учётной записи AD).

**`VectorIndex`**: `upsert(chunk_id, vec, partition, meta)`, `knn(query, k, filter)`, `rebuild()`; реализации sqlite-vec, позже usearch/LanceDB.

**`Embedder`**: `embed_docs`, `embed_query`, `model_id()`, `dims()`; реализации fastembed (в процессе-индексаторе) и провайдерская (Ollama/LM Studio `/api/embed`).

**`ChatProvider`**: `stream_chat(messages, tools?)`, `capabilities()`; реализации Ollama, OpenAI-compatible, Anthropic. Поверх — **`Policy`**: проверка «только локальные» на границе провайдера (не в UI) с чувствительностью на уровне папки/домена отправителя и локальным журналом обращений к внешним провайдерам.

## 5. ИИ-слой

### 5.1. Поиск естественным языком

Цель: p95 < 1 с без генерации; показанный список никогда не переставляется.

1. **Разбор запроса** (≤50 мс): детерминированный парсер — направление («мне писал» / «я писал» / «переписка с»), имена через словарь уменьшительных и транслита, относительные даты по-русски («в прошлом месяце», «перед Новым годом», «летом 2024»), фразы в кавычках, артикулы/числа. Сырые слова темы идут в FTS как есть. Маленькая LLM (3–4B, JSON-schema) — асинхронная доводка хвоста запросов и кэш разборов; LLM-разбор на CPU стоит 1–3 с и в быстрый путь не попадает.
2. **Резолв контакта** (трёхслойный): статический словарь ~400 имён с уменьшительными и гендерной неоднозначностью плюс транслит по ГОСТ 7.79 / ICAO / BGN; GAL и локальный индекс корреспондентов с частотой и давностью; обучение алиасов по подписям («С уважением, …» в письмах с конкретным адресом). Jaro-Winkler ≥0,85, нормализация ё→е, снятие падежа. Чип «от: …» с 2–3 альтернативами; при <3 результатах фильтр по отправителю ослабляется с пометкой. Метрика: top-1 ≥95 %, top-3 ≥99 % на 100 упоминаниях.
3. **FTS5** (≤50 мс): предстеммленная теневая колонка + сырая для точных фраз; trigram-индекс на тему/отправителя/коды. Фильтры (from, даты, папка) применяются до top-k.
4. **Векторы** (≤150–300 мс): KNN по чанкам (UniqueBody + префикс «Тема, От, Дата», 200–400 токенов) в партиции по году с предфильтром по контакту/дате; bit-скан + рескоринг топ-200–300 по int8.
5. **RRF** (k=60, топ-100 из каждого плеча), свёртка чанк→письмо→тред, дедупликация по InternetMessageId, взвешивание в пользу FTS при кавычках/числах и в пользу векторов при длинных формулировках.
6. **Реранкер** — bge-reranker-v2-m3 или jina-reranker-v2 (non-commercial — проверить лицензию) только при GPU и в бюджете 250–300 мс.
7. **Покрытие**: индикатор по папкам и годам; на несинхронизированном диапазоне — серверный `FindItem` (если подтвердится в спайке).

Текст вложений (docx/xlsx/pdf без OCR) — отдельные чанки с тегом типа: предмет деловой переписки часто лежит в приложенной таблице.

### 5.2. «Совет» при ответе

Контекст по иерархии (цель ≤6–8k токенов для локальных 7–9B, до 20k для API): последние 5 писем полным UniqueBody, старшие — инкрементальным саммари треда; участники с ролями (автор vs CC); 2–3 связанных треда одной-двумя фразами и id (связь по общим участникам и времени, без LLM); 3–5 моих писем этому адресату для стиля; **стилевой профиль контакта** как жёсткие ограничения (ты/Вы, приветствие, отчество, подпись, род пользователя из Sent); направление и тон. Вывод: короткий совет с цитатами `[msg:ID]` на каждое утверждение (чипы с переходом к письму), один черновик, кнопки «Вставить»/«Заменить», доработка чипами «мягче/короче». Всё стримится в блок с зарезервированной высотой.

Защита от галлюцинаций — механическая: извлечь из черновика числа, даты, суммы, имена и проверить их вхождение в контекст, непроверенное подчеркнуть; плейсхолдеры «[уточнить дату]» вместо выдумывания; температура 0,2–0,3 для совета. Письмо — недоверенный ввод: перед подачей в модель вырезать скрытый текст (display:none, нулевой кегль, zero-width); черновик никогда не отправляется сам.

### 5.3. Агент с инструментами (этап 2)

Клиент как MCP-хост (rmcp): поиск по почте — первый инструмент, корпоративные документы и интернет — внешние MCP-серверы. Границы: инструмент почты read-only, у агента нет инструмента «отправить письмо», allowlist доменов для веб-инструмента, подтверждение человеком любого исходящего действия — иначе письмо с инструкцией становится каналом утечки «агент ищет в почте → уносит через веб».

### 5.4. Модели

- **Эмбеддинги**: bge-m3 (dense + sparse, 8192 токенов, сильный ru↔en) остаётся безопасным выбором при GPU; на CPU — multilingual-e5-base/small (префиксы `query:`/`passage:` обязательны). Кандидаты на переоценку по собственному золотому набору: FRIDA (лидер ruMTEB-retrieval, 512 токенов, нужен собственный ONNX-экспорт), Giga-Embeddings-instruct-480M-0826 (MIT, 8192 токенов, уровень FRIDA), USER-bge-m3. Решение — по своему набору, не по лидерборду.
- **LLM локально**: T-lite-it-2.1 (Qwen3-8B, Apache-2.0, сильный русский и tool-calling) для 8–12 ГБ VRAM; T-pro-it-2.1 (32B) для 24 ГБ; Qwen3.5-9B / Gemma 4 12B как мультиязычные альтернативы (у Qwen3.5 выключить thinking для разбора запроса); GigaChat3.1-10B-A1.8B как кандидат для быстрого парсинга. Ollama и LM Studio говорят и OpenAI-, и Anthropic-форматом, так что trait сводится к двум протокольным адаптерам; на forced `tool_choice` и prompt caching не полагаться.
- **Облако и свои серверы**: в MVP разрешены любые API (решение автора 16.10.2026). Основной сценарий — OpenAI-совместимый endpoint на собственной GPU-машине автора; облачные API — для максимального качества «Совета». Профили подключений в настройках: быстрая модель для разбора запросов, сильная для «Совета», отдельная для эмбеддингов, отдельная для обезличивания (режим D); переключение без перезапуска. Режимы приватности и шлюз моделей — раздел 5.6.

### 5.5. Как измерять

Золотой набор 150–300 запросов из собственного ящика с разметкой на уровне тредов (0/1/2) по типам (русский разговорный 35 %, английский 15 %, смешанный 15 %, только имя 10 %, только дата 10 %, опечатки/транслит 10 %, коды 5 %) плюс синтетические 300–500 вопросов, сгенерированных LLM по случайным письмам. Метрики: Recall@10 ≥0,85, nDCG@10 ≥0,6, MRR, постадийно F1 разбора, top-1 контакта, recall@100 до реранка, p50/p95. Бинарник `aiowa eval`, прогон на каждое изменение. Для «Совета» — 30–50 сценариев с рубрикой (обоснованность, следование направлению, тон, ты/Вы, отсутствие новых фактов), LLM-судья плюс ручной журнал: из 20 реальных ответов ≥10 отправлены с правкой <30 % текста. Золотой набор содержит реальную переписку и хранится вне репозитория или зашифрованным. Ворота между ИИ-этапами: векторы включаются в прод, только если дают ≥10 пунктов Recall@10 к FTS-базе; реранкер — если ≥3–5 пунктов nDCG@10 в бюджете.

### 5.6. Шлюз моделей и режимы приватности

Все обращения к языковым моделям идут через один компонент `ModelGateway`: сборка контекста → `Policy` → при необходимости `Redactor` → провайдер → при необходимости обратная подстановка → журнал. Режимы задаются политикой в одном месте, а не разбросаны по функциям, чтобы переключение не требовало переписывать «Совет» или поиск.

Режимы (политика автора от 16.10.2026; MVP работает в режиме A, остальные закладываются в архитектуру сразу):

- **A. Любые модели.** MVP: только автор и его ящик. Облачные API и собственные серверы без ограничений, журнал обращений ведётся с первого дня.
- **B. Только локальные и свои серверы.** Внешние провайдеры отключены на уровне шлюза, в интерфейсе их нет.
- **C. Доверенные облачные.** Белый список провайдеров и моделей, утверждённый ИБ; остальные недоступны.
- **D. Облако после обезличивания.** Контекст проходит через локальный `Redactor`, в облако уходит обезличенная версия, ответ возвращается с обратной подстановкой.

Устройство `Redactor` для режима D:

1. **Структурный слой.** Контекст собирается не как сплошной текст, а как типизированные поля: участники (имя, адрес, роль), тема, тела, суммы, даты, вложения. Поля с известной семантикой заменяются детерминированно: `Иван Петров` → `[ЧЕЛОВЕК_1]`, `ООО «Ромашка»` → `[ОРГАНИЗАЦИЯ_1]`; адреса, телефоны, ИНН/КПП/ОГРН, номера счетов и карт, паспортные данные — по регулярным выражениям и словарям (GAL, список контрагентов).
2. **Слой распознавания сущностей.** Локальная NER-модель для русского (ONNX, на ноутбуке или GPU-сервере) находит имена, организации, локации и суммы в свободном тексте тел писем; порог чувствительности настраивается.
3. **Слой проверки локальной LLM** (опционально). Маленькая локальная модель получает уже обезличенный текст и отвечает, остались ли в нём чувствительные данные; при «да» фрагмент вырезается целиком.
4. **Карта подстановок** живёт только в памяти процесса на время запроса (`zeroize` после ответа); в журнал пишутся факт и категории заменённого, не значения.
5. **Обратная подстановка** в ответе облачной модели по той же карте; плейсхолдеры, которых нет в карте, подсвечиваются как подозрительные.
6. **Контроль качества.** Набор из 100–200 писем с ручной разметкой чувствительных данных; метрика recall по категориям (пропуск хуже ложной замены); обязательный предпросмотр отправляемого при первом включении режима.

**Вариант D2 (идея автора, 16.10.2026): обезличивание на этапе индексации, а не на каждый запрос.** Локальная модель один раз обрабатывает каждое письмо и вложение и сохраняет рядом с оригиналом обезличенную версию, где чувствительные данные заменены стабильными ссылками: `⟦P17⟧` для человека, `⟦O3⟧` для организации, `⟦ACC1⟧` для счёта. Словарь ссылок (vault) хранится только локально в зашифрованной базе. Облачная модель работает исключительно с обезличенным корпусом, включая эмбеддинги, и оставляет ссылки в ответе там, где они нужны; локальная модель при возврате подставляет реальные значения с правильным склонением. Преимущества перед обезличиванием на лету (D1): стоимость один раз, а не на каждый запрос; стабильные ссылки позволяют облачной модели рассуждать между тредами («⟦P17⟧ обещал скидку в прошлом месяце»); обратная подстановка в основном детерминированная, LLM нужна только для русской морфологии. Цена: единый словарь становится самым ценным секретом на машине (та же защита, что у базы писем); ошибки распознавания фиксируются в индексе, значит нужна версия обезличивателя и фоновая переобработка при его улучшении; квазиидентификаторы (даты, суммы, должности, стиль) могут раскрывать личность косвенно; облачные модели иногда искажают плейсхолдеры, нужен устойчивый формат и проверка, что каждая ссылка в ответе есть в словаре. **Вердикт проверки (16.10.2026, `docs/pseudonymization-design.md`):** схема жизнеспособна в усечённом виде «D2-lite» и только для переписки низкой и средней чувствительности. Три изменения обязательны. (1) Стабильные ссылки живут только в локальном словаре и в интерфейсе; на провод к провайдеру уходят одноразовые сессионные алиасы, иначе один пропуск распознавателя раскрывает сущность во всём корпусе. (2) Корпус не покидает машину: поиск и эмбеддинги локальные, облако получает обезличенные top-k фрагментов под конкретный запрос и генерирует без состояния; RAG по обезличенному тексту в литературе теряет качество сильнее всего. (3) Обезличивает конвейер «правила с контрольными суммами → газетир из адресной книги с морфологией → компактная NER», локальная LLM только верификатор спорных мест; переписывание 100 ГБ моделью на CPU ноутбука невозможно, на GPU-серверах автора возможно как дополнительный проход. HR, юридические, медицинские, зарплатные письма и ИБ-инциденты остаются только локальными; юридически это псевдонимизация, данные остаются ПДн. Включать режим можно после измерений на золотом наборе по порогам раздела 7 документа. Русский прецедент конвейера существует (pii-guard, rubert-base-pii-ner). Что заложить уже в MVP, чтобы не переделывать: типовая изоляция `Redacted`/`Plain` в Rust, белый список выгружаемых полей, единая функция извлечения текста с разбором цитат, классификация endpoint-ов в Policy, локальный поиск, детекторы ИНН/ОГРН/СНИЛС/счетов, схема словаря с версиями, журнал с хэшем отправленного.

Ограничения режима D, которые надо честно показать ИБ: обезличивание не абсолютно (контекст может раскрывать личность косвенно), качество «Совета» падает из-за потери имён и деталей, а стиль письма сам по себе может быть идентифицирующим. Режим D — компромисс для переписки средней чувствительности, не замена режиму B для самой чувствительной.

Этапы: MVP у автора в режиме A → обкатка на ящиках сотрудников без чувствительных данных (режим по решению ИБ) → решение о развитии и выбор между B, C и D.

## 6. Данные и производительность на ящике около 100 ГБ

Все числа — оценки с явными допущениями; подсчёт по `folder:TotalCount` и `PR_MESSAGE_SIZE_EXTENDED` ещё не делался, и доступность этих свойств через OWA JSON не проверена.

**Допущения.** 75–85 % объёма — вложения, остающиеся на сервере. Писем 450 тыс.–1 млн (эксперты расходятся вдвое). HTML-тело в среднем ~35 КБ, UniqueBody ~2 КБ, 1–1,5 чанка на письмо после очистки → 0,6–1,5 млн чанков.

**Локальная база без вложений** (для 450 тыс. писем; для 1 млн умножать примерно на два): метаданные и индексы 0,7–0,9 ГБ; HTML-тела 2,0–2,6 ГБ при zstd с обученным словарём (3–4 ГБ без словаря); FTS5 по UniqueBody 0,7–1,1 ГБ (по полному тексту с цитатами 2,5–3,5 ГБ, trigram ещё ×3 — поэтому только на короткие поля); векторы 600 тыс. × 1024d: f32 2,4 ГБ, int8 0,6 ГБ, bit 77 МБ. Итого базовый вариант 4–6 ГБ, худший 10–11. Кеш вложений отдельно, LRU 5–20 ГБ с дедупликацией по хэшу. Пик WAL при массовой загрузке удваивает диск — `wal_checkpoint(TRUNCATE)` каждые N тысяч писем, `auto_vacuum=INCREMENTAL`. Расположение — `%LOCALAPPDATA%\AIOWA`, не Documents/OneDrive.

**Синхронизация.** `SyncFolderItems` отдаёт ≤512 изменений за вызов → метаданные всего ящика за 8–20 минут. Тела через `GetItem` пачками ≤50: без троттлинга 50–100 писем/с на поток, но бюджет Exchange считается в миллисекундах серверного времени и, по памяти экспертов (не сверено с `Get-ThrottlingPolicy`), типовая политика 2013+ даёт устойчиво ~15 минут серверного времени в час — около 75 тыс. тел/ч независимо от параллелизма, то есть 6–8 ч по LAN и 8–12 ч через VPN; бюджет делится с открытой в браузере OWA. Ежедневный инкремент — секунды. Поллинг новых писем в v1 — только Inbox каждые 30–60 с, остальные папки раз в 5–15 мин; push-канал OWA не документирован и отложен.

**Эмбеддинги.** Для 1024-мерной модели класса XLM-R-large (bge-m3, e5-large): ≈21 док/с на 16-ядерном десктопе (измерено независимо), заметно меньше на ноутбуке → 1 млн чанков это от ~13 ч на сильном десктопе до нескольких суток на ноутбуке; e5-small — в ~10 раз быстрее (1–2 ч); GPU класса RTX 3060/4060 — 2–4 ч для bge-m3. Резидентная память: bge-m3 fp32 ≈2,3 ГБ + активации 1–2 ГБ (нужно 16 ГБ ОЗУ), e5-small ≈0,5 ГБ. Отсюда: 5-минутный калибровочный бенчмарк на первом запуске выбирает модель автоматически; индексация — в отдельном процессе с пониженным приоритетом и EcoQoS, только от сети и в простое; версия модели хранится на таблице векторов для фоновой перемиграции.

**Векторный поиск.** sqlite-vec 0.1.9 — brute force: f32 1 млн × 1024d ≈ 590 мс на M4 по бенчмарку автора (на обычном CPU и с холодным кешем — секунды); int8 200–500 мс; bit-скан + рескоринг топ-300 ≈ 50–100 мс при recall ~95–99 %. Партиция по году и предфильтр по контакту (типичный запрос «от …» — 0,1–2 % корпуса) сводят скан к тысячам векторов. ANN в v1 не нужен; usearch/LanceDB подключаются, если p95 нефильтрованного запроса превысит 400 мс.

**Бюджет латентности поиска:** разбор ≤50 мс, эмбеддинг запроса 30–80 мс (модель прогрета; холодная загрузка 1–3 с), FTS 20–50, векторы 50–300, RRF 10–20 → 150–450 мс. Нарушители: реранкер на CPU (6–16 с на топ-20 для bge-reranker-v2-m3) и LLM-разбор (1–3 с) — оба вне быстрого пути.

**Первый запуск (LAN, 450 тыс.):** 0–10 с — вход, иерархия папок, счётчики и честный прогноз («≈5 ГБ, ~7 ч»); до 2 мин — Входящие и Отправленные за 30 дней с телами, клиентом можно пользоваться; до 20 мин — все метаданные; 1–8 ч — тела от свежих к старым; эмбеддинги по приоритетам: открытые треды → Входящие+Отправленные за 12–24 месяца → остальное. Исключить из индексации Junk, Deleted Items, Conversation History, уведомления (Auto-Submitted, Precedence: bulk, List-Unsubscribe) — 30–50 % писем; дедупликация чанков по хэшу — ещё 10–20 %.

**Память приложения:** WebView2 250–400 МБ, Rust-ядро 50–100 МБ, page cache 128–256 МБ. Цель «≤400 МБ при ящике 100 ГБ» несовместима с резидентной bge-m3 и вторым WebView2 для встроенной OWA — реалистичная цель для основного процесса 500–700 МБ, индексатор отдельно.

## 7. Безопасность и приватность

Главная проблема не техническая: для службы ИБ это самодельный PST на 100 ГБ плюс потенциальный канал в облачные модели. Для MVP у автора действует режим A (любые модели, раздел 5.6); к этапу обкатки на ящиках сотрудников дефолт ужесточается по решению ИБ до одного из режимов B, C или D, и именно ради этого шлюз моделей и журнал обращений строятся с первого дня.

**Обязательно в v1**
- Cookies сессии — bearer-токен на весь ящик: в памяти через `secrecy`/`zeroize`, на диск только через DPAPI (user scope), в логи и debug-вывод никогда; выход — вызов `/owa/logoff.owa`, а не удаление cookies. Credential Manager ограничен малым размером blob (по данным эксперта ~2,5 КБ, не проверено) — хранить там только мастер-ключ, cookies и ключ БД — в файле, зашифрованном им.
- Один 401/440 после одной попытки повторного входа переводит все задачи в `AuthRequired` без автоматических повторов — защита от блокировки учётной записи AD при смене пароля.
- Локальная база: SQLCipher (если спайк подтвердит совместимость с FTS5 и `sqlite3_auto_extension` sqlite-vec) с ключом в Credential Manager; проверка BitLocker при первом запуске; эмбеддинги частично обратимы (vec2text) и живут в той же зашифрованной базе; LanceDB шифрования at rest не имеет — аргумент против.
- HTML писем: ammonia в Rust при сохранении (script/iframe/form/object/meta refresh, `javascript:`/`data:` в href, `@import`/`url()` в CSS) + `<iframe sandbox srcdoc>` без `allow-scripts`/`allow-same-origin` и CSP `default-src 'none'; img-src cid: data:`; серверному `NormalizedBody` не доверять как «безопасному». Удалённые картинки выключены; при разрешении — загрузка из Rust без cookies/Referer с запретом RFC1918 (защита от зондирования внутренней сети письмом). Ссылки — в системный браузер с показом реального URL и punycode.
- Вложения: временный файл с Mark-of-the-Web (Zone.Identifier=3), чтобы сработали Protected View и SmartScreen; список блокируемых расширений как Level-1 в Outlook; .html/.svg/.eml не рендерить inline; кеш зашифрован; temp чистится.
- Модели: политика автора (16.10.2026). MVP только у автора и с его ящиком: разрешены API любых моделей, облачных и локальных. Все обращения идут через шлюз с режимами (раздел 5.6): A любые модели (MVP), B только локальные и свои серверы, C доверенные облачные по белому списку, D облако после обезличивания локальной моделью. После обкатки на ящиках сотрудников без чувствительных данных ИБ выбирает режим для дальнейшего развития. Обязательными с первого дня остаются предпросмотр отправляемого контекста по требованию, локальный журнал «что, когда и какому провайдеру ушло» и авто-блок внешних провайдеров по меткам MIP (`msip_labels`), IRM/S-MIME и ключевым словам в теме. Предупреждение эксперта по ИБ (регионы поддержки Anthropic/OpenAI, retention без ZDR, 152-ФЗ при трансграничной передаче) не проверено и остаётся пунктом для досье к этапу обкатки.
- IRM/RMS-защищённые, S/MIME и помеченные MIP письма: не кэшировать тело, не индексировать, не отдавать в модель; удаления и retention сервера зеркалятся локально.
- Ноль внешней телеметрии и crash-репортинга; `tracing` со слоем редакции (ни тем, ни адресов, ни тел, ни cookies на любом уровне); локальные метрики индексатора допустимы и остаются на машине — в досье для ИБ эти термины разводятся явно. Модели для fastembed не качать молча с Hugging Face — бандлить или качать явным действием с проверкой sha256; шрифты без CDN, CSP Tauri `default-src 'self'`.
- TLS через `rustls-platform-verifier` (корпоративный CA, TLS-инспекция), без `danger_accept_invalid_certs`. Честный `User-Agent: AIOWA/x.y` — он виден в IIS-логах, имитация Edge будет расценена как обман.
- Окно входа — отдельное окно Tauri без IPC-capabilities; встроенная OWA (strangler-вкладка) — отдельный webview с пустым набором capabilities, перехватом загрузок и внешних ссылок.
- Tauri 2: минимальные capabilities (без shell, fs только в каталог приложения), `assetProtocol` scope только на кеш вложений.
- Гигиена разработки: синтетические фикстуры или псевдонимизированные реальные с тестом scrubber «в выходе нет адресов из allowlist реальных доменов»; gitleaks в pre-commit; `.gitignore` на `*.db` и логи; реальную переписку не вставлять в контекст ИИ-ассистента.

**Опционально, но поднимает шансы у ИБ**
Подпись Authenticode (внутренний CA компании на пилоте, OV-сертификат при выходе наружу; Azure Artifact Signing недоступен); cargo-audit/cargo-deny; привязка ключа к Windows Hello/TPM; `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` против Recall и захвата экрана; пометка буфера обмена `ExcludeClipboardContentFromMonitorProcessing`; кнопка «стереть всё»; автоочистка базы после N дней без успешного входа; локальный журнал «что, когда и какому провайдеру ушло».

## 8. Дизайн

**Принципы.** Нативность (Mica в базовом слое, системный акцент через `UISettings::GetColorValue`, Segoe UI Variable, Fluent-скроллбары `scrollBarStyle: fluentOverlay` — требование к версии WebView2 проверить, тёмный заголовок окна), сдержанность (одна акцентная роль, один набор иконок Fluent UI System Icons 20 Regular/Filled, движение только на смену состояния), отсутствие джанка (фиксированные высоты строк, табличные цифры, резерв места под ИИ-панель, окно показывается после первого кадра оболочки — `visible:false` + `noRedirectionBitmap`). Макет обязан выглядеть законченным на сплошном фоне: Mica падает в #F3F3F3/#202020 при неактивном окне, выключенной прозрачности и экономии батареи, а Tauri на Windows 10 молча оставит прозрачное окно.

**Слои.** Mica только под заголовком и панелью папок; список и область чтения — непрозрачные (#F9F9F9 / #282828): это и гайдлайн Microsoft (Mica base + Layer), и способ сохранить LCD-сглаживание текста в Chromium, и дешёвый ресайз. Инверсию цветов писем не делать; в тёмной теме письмо — белая «бумага» max-width 720 px с радиусом 8 внутри sandbox-iframe.

**Дизайн-система.** Один `tokens.css`, сгенерированный из `@fluentui/tokens` (MIT, но вечный `1.0.0-alpha.N` — пиновать) с переопределениями WinUI: поверхности, текст (fg1 #242424 / #FFFFFF, fg2 #424242 / #D6D6D6, fg3 #616161 / #ADADAD), акцент (`AccentDark1`/`AccentLight2` для заливки, fallback #005FB8 / #60CDFF), обводки, тени (shadow8/16/28/64), радиусы 4 (контролы) / 8 (карточки, флайауты, окно), длительности 100/150/200 мс с кривыми `cubic-bezier(.1,.9,.2,1)` на вход и `(.9,.1,1,.2)` на выход (Microsoft для WinUI публикует 83/167/250/333 мс — выбрать один набор и записать в токены). Типографика: Caption 12/16, Body 14/20, Body Strong 14/20 Semibold, Body Large 18/24, Subtitle 20/28, Title 28/36; заголовки 600, не 700 (кириллический bold превращается в пятно); `letter-spacing: 0`; `tabular-nums` на датах и счётчиках; `lang="ru"`; Sentence case; русские строки длиннее английских на 15–25 % — никаких фиксированных ширин кнопок. Шрифт: Segoe UI Variable через `@font-face { font-family: X; src: local('Segoe UI Variable Text'); font-weight: 100 900 }` (только так работают opsz и промежуточные веса), fallback Inter/Golos для не-Windows 11.

**Плотность и панели.** Строки Compact 32 / Cozy 56 (по умолчанию, без аватаров) / Roomy 72 px; навигация 240 px (рейка 48), список 360 px (280–480), чтение — остаток, min 520; ниже 1100 px — две панели. Сетка 4 px, контролы 32 px.

**«Тихий» ИИ.** Ни звёздочек, ни градиентов, ни отдельного цвета: «Совет» — обычная subtle-кнопка в тулбаре ответа; маркер режима — чип Caption «ИИ · локально · <модель>» всегда на виду; прогресс — линия 2 px, не спиннер; стрим в блок с min-height; разобранный запрос — редактируемые чипы-пилюли 24 px.

**Палитра и клавиатура.** Ctrl+K в редакторе OWA — «вставить ссылку», поэтому глобально Ctrl+K, в фокусе редактора — ссылка, дублёр Ctrl+Shift+P, «/» — поиск. Четыре схемы OWA (Outlook, Outlook.com, Gmail, Yahoo), оверлей «?», F6 между панелями, отключение акселераторов WebView2 (Ctrl+F, F5, Ctrl+P), менеджер фокуса «после удаления выделить следующее». Фокус-кольцо в стиле Windows 11 только на `:focus-visible`; roving tabindex и `aria-rowcount`/`aria-posinset` в виртуализированном списке; `forced-colors` отключает Mica и тени; масштаб текста в настройках приложения.

**Процесс.** Маршрут `/gallery` с переключателями light/dark/forced-colors/density/accent с первой недели; Playwright-скриншоты в Chromium как визуальная регрессия; Stylelint-запрет сырых hex/px вне токенов. Компоненты первой необходимости — около 15 (Button, IconButton, Input, Chip, Menu, Tooltip, Dialog, InfoBar, ProgressBar, ListRow ×3, Splitter, Tabs, Avatar, CommandPalette, Skeleton).

Операции записи и ответ** | Только после тестового ящика: перемещение/удаление с локальной корзиной и отменой 10 с; outbox `CreateItem(SaveOnly) → SendItem → сверка Sent Items` с собственным InternetMessageId; редактор TipTap StarterKit с цитированием в стиле OWA; автосохранение черновиков на сервер | 2 недели без потерь и дублей при ежедневной сверке счётчиков папок; матрица «ответ из приложения → просмотр в Outlook desktop/OWA/мобильный» пройдена | 4–6 нед |

## 11. Решения, которые нужно принять автору

1. **Что выяснить у админов и ИБ до первой строки кода.** (Статус 16.10.2026: опросник подготовлен, `docs/questionnaire-admins-security.md`; вопрос о переезде в M365 снят, облака не будет по позиции ИТ, у админов уточняются только сроки перехода на SE и остальные пункты.) Варианты: (а) один опросник с командлетами сейчас; (б) писать код, узнавать по факту. **Рекомендация: (а).** Опросник: план миграции (SE in-place / M365 / остаёмся), `Get-OrganizationConfig | fl EwsEnabled,EwsApplicationAccessPolicy,Ews*List,ActivityBasedAuthenticationTimeout`, `Get-ThrottlingPolicy`, `Get-OwaMailboxPolicy` (AllowOfflineOn, вложения), `Get-OwaVirtualDirectory` (тип аутентификации, FBA-таймауты), ADFS token lifetime, наличие архивного ящика и holds, политика ИБ по локальным копиям и внешним LLM, допустимость нестандартного User-Agent, тестовый ящик. Почему: ответ «M365 через полгода» меняет транспорт, аутентификацию и модель id — 30–40 % кода v1; один разговор экономит до двух месяцев.

2. **Объём v1.** Варианты: (а) «компаньон» рядом с OWA без отправки (13–19 нед); (б) ядро чтения + FTS + ответ, остальное — встроенная OWA (8–10 нед после спайка по одной оценке, вдвое больше по другой); (в) паритет с приглашениями, напоминаниями, mailto, pop-out. **Рекомендация: (б) в порядке «чтение → ИИ-поиск → запись», с strangler-вкладкой.** Почему: слой sync+SQLite нужен в любом варианте, локальный поиск уже даёт ежедневную ценность, встроенная OWA закрывает остальное с первого дня; отправка ждёт тестового ящика. Эксперты расходятся по срокам вдвое — это аргумент за таймбоксы и контрольные точки, а не за точные недели.

3. **Транспорт фоновой синхронизации.** Варианты: (а) OWA JSON основной, EWS «когда-нибудь» (концепт); (б) недельный спайк EWS SOAP с Negotiate и EWS как основной канал sync при успехе; (в) однодневная проверка EWS в спайке, реализация только при провале OWA JSON или если TTL сессии не позволяет фон. **Рекомендация: (в).** Почему: для Negotiate/NTLM в reqwest нет готовой интеграции (нужны sspi/libcurl/WinHTTP), EWS может быть закрыт политикой, доменность машины неизвестна — тратить неделю на страховку до того, как измерен TTL основной сессии, преждевременно; но знать, существует ли страховка, нужно до старта v1.

4. **Профиль webview для входа.** (Снижен в приоритете: на сервере автора forms-based auth без MFA, вход идёт программно из Rust; webview нужен только как запасной путь.) Варианты: (а) постоянный user-data-folder WebView2 — тихий SSO-вход через ADFS/Kerberos без пароля (риски, продукт); (б) InPrivate-окно без следов на диске (ИБ). **Рекомендация: выделенный постоянный профиль только для входа, отдельный от рендера писем, в `%LOCALAPPDATA%`, с опцией «не запоминать сессию» для требовательной ИБ.** Почему: без тихого повторного входа фоновая синхронизация под MFA невозможна, а продукт теряет смысл; изоляция профиля от писем и honest-опция дают ИБ понятный ответ. Чтение cookies из InPrivate-профиля через Tauri никто не проверял.

5. **Шифрование локальной базы.** Варианты: (а) только BitLocker; (б) SQLCipher с ключом в Credential Manager, прозрачно для пользователя; (в) SQLCipher + пароль/Windows Hello на каждом запуске. **Рекомендация: (б), если спайк подтвердит работу `bundled-sqlcipher` с FTS5 и регистрацией sqlite-vec через `auto_extension`; `StoreOpener` принимает `Option<Key>` с первого дня.** Почему: утверждение «SQLCipher ломает расширения» никто не проверил, а копирование папки, бэкап и OneDrive BitLocker не закрывает; (в) ломает фоновый старт ради защиты от малвари в сессии, от которой всё равно спасает EDR.

6. **Модель эмбеддингов и глубина индексации.** Варианты: (а) bge-m3 по всему ящику; (б) e5-small/base с окном 2–3 года; (в) аппаратно-адаптивно с перемиграцией. **Рекомендация: (в): e5-base на CPU, bge-m3 (или Giga-Embeddings-480M / FRIDA после оценки) при GPU; FTS на всё сразу, векторы за 24 месяца первыми, остальное фоном с видимым покрытием.** Почему: на ноутбучном CPU 1024-мерная модель — суток, e5 — часы; ruMTEB показывает, что русские модели уже обходят bge-m3 на retrieval, но выбирать надо по собственному золотому набору. Наличие нужных моделей в fastembed-rs проверить в спайке.

7. **Векторное хранилище.** Варианты: sqlite-vec стабильный с int8/bit и партициями; sqlite-vec alpha с DiskANN; LanceDB; usearch-сайдкар. **Рекомендация: sqlite-vec 0.1.9 за trait, usearch/LanceDB — вторая реализация только при p95 > 400 мс.** Почему: после резолва контакта и даты сканируются тысячи векторов — brute force быстрее любого графа; одна транзакционная база проще для одного разработчика; альфа с ANN имеет открытые баги.

8. **Провайдер LLM для «Совета» по умолчанию.** Решено автором 16.10.2026: в MVP (только автор, его ящик) разрешены API любых моделей, облачных и локальных; архитектура закладывает четыре режима приватности (раздел 5.6), а режим для дальнейшего развития выбирает ИБ после обкатки на ящиках сотрудников. Остаток решения: какой профиль по умолчанию для каждой задачи (разбор запроса, «Совет», эмбеддинги) — выбирается после замера качества и задержки на 30 сценариях; предпросмотр контекста и локальный журнал обращений сохраняются; режим «только локально» остаётся опцией. Исходная рекомендация экспертов (локальные по умолчанию, облако только с РФ-хостингом) снята автором; её аргументы сохранены в разделе 7 для досье ИБ.

9. **Фронтенд и дизайн в v1.** Варианты: Svelte 5 + Bits UI; SolidJS + Kobalte + cmdk-solid; Leptos/Dioxus; и отдельно — Mica/кастомный заголовок/Segoe в v1 или после. **Рекомендация: Svelte 5 + Bits UI + TanStack Virtual (или virtua); в v1 — токены, Segoe UI Variable через `local()`, непрозрачные поверхности и нативные decorations; Mica базового слоя и кастомный заголовок — этап 5 за флагом.** Почему: готовые доступные примитивы (палитра, меню, диалог) есть в одной библиотеке; дизайн-система нужна с первого дня (иначе дрейф), а материалы и заголовок — после ежедневного использования.

10. **Тестовый ящик и режим записи.** Варианты: (а) отлаживать запись на рабочем ящике; (б) запросить тестовый ящик, боевой — read-only до чек-листа. **Рекомендация: (б).** Почему: дубль письма коллегам — самая дорогая ошибка недокументированного API для репутации проекта.

11. **Git и фикстуры.** (Статус 16.10.2026: репозиторий github.com/zergont/AIOWA заведён автором; остаются локальная инициализация, `.gitignore` и первый коммит.) Вопрос автора «пока локально, потом в Git?». Варианты: (а) без git до v1; (б) локальный `git init` с первого коммита, приватный remote при появлении контрактных тестов/CI; (в) сразу публичный GitHub. **Рекомендация: (б).** Почему: фикстуры реверс-инжиниринга, результаты спайка и схема БД — артефакты, к которым придётся возвращаться при решении «убить/продолжать»; стоимость `git init` — минуты. Фикстуры в репозитории — только после scrubber с тестом на отсутствие реальных адресов и хостов; золотой набор запросов — вне git или зашифрованным; `.gitignore` на базы, логи, cookies; gitleaks в pre-commit. Первый коммит — этот документ и ADR-ы.

12. **Аудитория, лицензия, имя.** (Частично решено 16.10.2026: MVP только у автора; следующий этап — обкатка на ящиках сотрудников без чувствительных данных, значит подпись внутренним ЦС, установщик и досье для ИБ нужны к этому этапу, а не к MVP.) Варианты: личный инструмент; клиент для коллег; публичный open source. **Рекомендация: записать «аудитория v1 = автор», выбрать лицензию кода и завести `THIRD_PARTY_LICENSES` с проверкой cargo-deny и списком лицензий моделей (jina-reranker-v2 и jina-embeddings-v3 — non-commercial, Gemma — своя лицензия, YandexGPT 5 Lite — лимит токенов); при выходе за личное использование переименовать проект, убрав «OWA» (товарный знак Microsoft).** Почему: от этого зависят подпись, досье, допустимые модели и совместимость MPL-2.0 крейта `ews`.

## 12. Что ещё не учли

- **Несколько учётных записей и устройств, архивный ящик.** `account_id` во всех таблицах с первой миграции; In-Place Archive как второй корень папок; работа на двух машинах решается принципом «состояние на сервере» и экспортом/импортом локально-уникальных данных.
- **Резервное копирование и экспорт.** Стилевые профили, словарь алиасов, золотой набор, настройки нигде не синхронизируются — нужен экспорт в один зашифрованный архив (палитра и CLI), периодический `VACUUM INTO` снимок `meta.db` вне File History/OneDrive, экспорт писем в EML/mbox, чтобы труд индексации не пропал при смене транспорта.
- **Смена пароля домена и увольнение.** Документ «что делать при смене пароля»; никаких фоновых повторов после одного 401; опция автоочистки базы после N дней без входа.
- **Публикация OWA через reverse proxy / VPN и обнаружение сервера.** Копировать весь cookie-jar origin (не только `cadata*`); URL задаётся вручную с проверкой; спайк по всем реальным путям доступа фиксирует набор cookie и заголовков прокси.
- **Семантика «оффлайн».** Таблица «состояние соединения (Online / Throttled / AuthRequired / Offline / Metered) × действие → поведение»; один индикатор состояния; что делает поиск по несинхронизированному диапазону без сети.
- **Время, часовые пояса, имена папок.** Все даты в UTC, отображение в поясе Windows, `TimeZoneContext` из настроек OWA; относительные даты тестировать на границах суток/месяца/DST; папки — только по `DistinguishedFolderId`/`FolderId`, локализованное имя лишь как подпись.
- **Граничные случаи в тестовом корпусе.** 30–40 патологий: письмо с 2000 получателей, HTML 5 МБ, вложение 100 МБ, пустой UniqueBody, одно письмо в пяти папках, тред из 300 писем, встречи и автоответы по ItemClass, вложенные .eml/.msg, cp1251/koi8-r без объявления, S/MIME и IRM.
- **Совместимость при одновременном обновлении приложения и сервера.** Матрица «версия приложения × build Exchange × версия схемы»; безопасный режим «локальная база только для чтения»; миграции вперёд-совместимы на одну минорную версию.
- **Уведомления о новой почте и их цена в бюджете троттлинга.** Поллинг десятков папок × 120 вызовов/ч конкурирует с первичной выкачкой; в v1 — только Inbox и папки с правилом «уведомлять»; push (OWA или EWS streaming) — спайк этапа 2.
- **Характеристики целевой машины** (сняты 16.10.2026): ноутбук, Intel Core Ultra 9 185H (16 ядер / 22 потока), 31 ГБ ОЗУ, Intel Arc iGPU (NVIDIA нет), диск C: около 18 ГБ свободно, D: около 52 ГБ свободно из 1,6 ТБ; Windows 11 Pro 26300; WebView2 Runtime 155; Node 22, Git 2.56, MSVC C++ (VS 18 Community) есть; Rust не установлен (ставить rustup с `CARGO_HOME`, `RUSTUP_HOME` и target-каталогом на D:); Ollama и LM Studio нет. Следствия: тяжёлые модели на GPU-машинах автора по сети, локальная база компактной (цель не более 10 ГБ без вложений), калибровочный бенчмарк эмбеддингов именно на этой машине. Не выяснено: присоединение к домену, BitLocker.
- **Единый набор целевых чисел.** Эксперты назвали холодный старт ≤1 с / <1,5 с / <500 мс и поиск p95 ≤300 мс / <1 с — для критериев готовности нужен один набор, зафиксированный в этапах выше (старт <1,5 с, поиск по 12 мес p95 <300 мс, полный гибрид p95 <1 с).
- **Windows-специфичные каналы утечки.** Recall на Copilot+ PC, облачная история буфера обмена, захват экрана в Teams — пометки окон и буфера (раздел 7, опционально) и запись в досье для ИБ.
- **Локализация как дизайн.** Формы множественного числа (1 письмо / 2 письма / 5 писем), формат дат в списке, Sentence case, «ёлочки», неразрывные пробелы, тексты пустых состояний.
